WordCraft vs Microsoft Word: A Free Rust Clone — How It Works, and What to Actually Use It For

By Bronze · October 31, 2026 · 7 min read

A small team built a word processor that looks and behaves like Word, in pure Rust, in a matter of weeks, with AI doing much of the writing. It reads and writes .docx, runs offline on desktop and in the browser, costs nothing, and — the part that matters most — lets an AI agent drive it through the same commands a human clicks.

That is WordCraft, from the ArtCraft team, and it is the most interesting free alternative to Word in years precisely because it is not finished. Its own roadmap calls it alpha and grades it at about 60% ready for real work. So this is not a "Word is dead" post. It is a comparison of what each tool actually is, how the clone works under the hood, where its own authors say it falls short, and the three jobs it is already good for today.

What each tool actually is

Microsoft Word is the reference implementation: decades of formatting edge cases, a subscription product inside an ecosystem of cloud storage, collaboration, and enterprise deployment. You pay for completeness and for the guarantee that the file your colleague sends you will open exactly as they wrote it.

WordCraft is a clean-room reimplementation: built, in its own words, "from public specifications and observation, with every asset original or openly licensed." Clean-room here has a specific meaning — the authors did not copy Microsoft's code. They re-created the behavior from the published .docx format, from watching how Word behaves, and from writing their own code. The project is MIT OR Apache-2.0 licensed, created on October 7, 2026, and had 16,750 stars on GitHub when checked on the morning of October 31, 2026.

The ArtCraft team did the same trick across a whole suite — PhotoCraft for Photoshop, GridCraft for spreadsheets, Deckcraft for slides — and Korean press coverage on October 30, 2026 (ChosunBiz) is what turned a GitHub curiosity into a story about the moat around big software. That coverage also carries the caveat this post keeps: a user interface that mimics Word this closely invites a copyright dispute even with a clean-room claim, and the professional feature set has not been independently proven. Treat the clone's legal safety as unresolved, not settled.

The mechanism: one command set for humans and agents

Most "AI-friendly" tools bolt an assistant on the side. WordCraft's design inverts that: every action is a command with an id, and the same command set drives the ribbon, the keyboard shortcuts, the command search, a command-line tool, a JSON control channel, and an MCP server. The README describes this set as 422 commands. (A small transparency note: the roadmap's measured count lists 433 commands — the two pages drift slightly, but the mechanism is the same on both.)

That single decision explains three things at once:

1. Why it is fast and portable. One Rust codebase, native egui on the GPU, no Electron, no Tauri. It ships on macOS, Windows, Linux, BSD, and the web via WebAssembly, with v0.4.0 released October 10, 2026 as signed builds. The README reports that typing in a 188-page document re-lays it out in about 1.4 ms because paragraph layout is cached — a vendor claim, but the architecture (cached layout, on-demand page rendering) is at least the right shape for it.

2. Why agents can use it without screenshots. An agent does not need to click buttons and read pixels. It connects over MCP (claude mcp add wordcraft), lists commands, executes them, and checks its own work with inspect_document — reading the document structure back instead of guessing from a screenshot. Macros record any sequence of commands and play it back. For document work, this is a much more reliable agent interface than screen-scraping a GUI.

3. Why offline is real here, not marketing. Spelling, grammar, and everything else work offline, according to the README. There is no account and no subscription because there is no server to pay for. The one exception to watch is the agent path itself: if you connect an agent that calls a cloud model, your document content travels to that model provider. Offline describes the word processor, not every agent you plug into it. WordCraft at least gives you the confinement flags to control this: wordcraft-cli mcp --automation-read-root DIR --automation-write-root DIR fences the agent to folders you name.

By area, the shape is clear: typing, selection, and clipboard at 85%; character and paragraph formatting at 82%; tables at 76%; review (comments, track changes, compare) at 72% — against charts, SmartArt, Draw/ink, and 3D models at 3%. Stability sits at 50%, ecosystem and plugins at 15%. The interface ships in many languages including a complete Vietnamese catalog — but Vietnamese proofing (spelling and grammar) is not included yet.

And the "why not beta" list, in the roadmap's own words: DOCX has never been tested on real-world files; charts, SmartArt, and OLE objects are dropped silently; pagination differs from Word; content controls are lost; there is open evidence of a startup crash and several hangs. The roadmap's user evidence is equally blunt: 120 issues from outside users, 4 praise, and 0 "switched from Word." Nobody, by their own count, has yet replaced Word with this.

Three jobs it is already good for

1. Draft and edit .docx offline, on any desktop. For straightforward documents — text, styles, lists, tables, track changes, mail merge from CSV, citations in APA, MLA, Chicago, or IEEE — the core workflows pass the project's own alpha gate end to end with save and reopen. Start from a copy, not the original, and keep Word around for the final check.

2. Batch-convert and inspect documents from the command line. wordcraft-cli convert report.docx report.pdf converts between docx, pdf, odt, rtf, html, md, tex, and txt; wordcraft-cli inspect report.docx dumps the structure as JSON; wordcraft-cli run --script job.json replays a command script and saves the result. That is a genuinely useful pipeline piece even if you never open the GUI.

3. Let an agent draft documents under confinement. Connect the MCP server, fence it to one input and one output folder with the --automation-read-root / --automation-write-root flags, and have it build a report from a template — then verify with inspect_document before opening the result. The agent writes a real .docx you own, with no subscription and no upload to a word-processor vendor. Do not yet give it files containing charts, SmartArt, or complex real-world formatting and expect them back intact.

What not to trust it with yet

Do not migrate a team onto it. Do not round-trip a client's .docx full of charts and expect the charts to survive. Do not assume pagination matches Word page-for-page — the roadmap says it does not. And do not read the star count as proof: 16,750 stars in three weeks measures excitement, and the project's own evidence says zero users have switched from Word so far. Excitement is a reason to try it; it is not a reason to depend on it.

The rule to keep

The interesting thing about WordCraft is not that a clone exists. Clones have existed for decades. It is that the clone was built command-first, so the same interface serves a human clicking a ribbon and an agent executing a script — and that it publishes a parity table honest enough to say 3% on charts and zero switchers. If you want a free Word today, the honest answer is: use WordCraft for drafting, batch work, and agent-driven documents, and keep Word for the files that must survive contact with everyone else unchanged. Revisit the split when the roadmap's beta list — real-world .docx testing, chart preservation, stability — is actually closed.
